## 2. Root cause — CONFIRMED

Three confirmed defects remain after prior phases (which already removed the `verify.js`
`ethers.Wallet.createRandom()` path and disabled `agentWalletManager.createAgentWallet`):

### 2.1 Password login loses the Circle identity — CONFIRMED
`functions/api/auth/login.js` returned only the legacy `wallet` structure and persisted a
session `{ email, userId, walletAddress }`. `verify.js` (OTP) returns `profile.circleWallet`
and persists `circleWalletId`/`circleWalletAddress`. After password login the frontend had
no Circle identity, so session restoration could not resolve the per-user Circle wallet.

### 2.2 Provisioning race (duplicate Circle wallets) — CONFIRMED
`functions/api/agent-signer/_circle.js:createUserWallet()` used `randomUUID()` idempotency
keys. `provision.js` used a read-before-create check. Two concurrent requests (double-click,
multi-tab, OTP + explicit provision race, Cloudflare retry) could both pass the check and
create two Circle wallets. `randomUUID()` makes each request a distinct Circle operation.

### 2.3 Legacy signer activation — CONFIRMED (not fully decoupled — see §7)
`shared/auth.js:_buildRemoteSigner()` builds a legacy custodial signer from
`_profile.wallet.address`; `shared/walletManager.js:activateFromAuth()` activates it as
`activeWalletType='intelligent'`. For legacy users this surfaces the "Internal Smart Wallet".
This is entangled with the x402 relayer (`index.html:43953` `AuthManager.signOnServer`), which
Section 11 forbids changing — so it is documented, not yet removed (see §7).

### 2.4 Misleading "Internal Smart Wallet" labels — CONFIRMED
The auth-success modal (`index.html`) defaulted to "Your Intelligent Wallet is ready" /
"Internal Smart Wallet" even for Circle-only users.

## 3. Wallet-creation call graph (before → after)

**Before** (relevant paths):
- `verify.js` new user → `wallet:{address:null,type:'none'}` + `createUserWallet` (Circle) ✅ already correct
- `login.js` → **no** Circle identity ❌
- `auth.js:_buildRemoteSigner` (from `_profile.wallet.address`) → `activateFromAuth` → legacy signer ❌
- `_circle.js:createUserWallet` → `randomUUID()` idempotency ❌
- `agentWalletManager.createAgentWallet/createWalletWithBackup` → `null` ✅ already disabled
- `walletManager.createOrRestoreWallet` → `null` when no vault ✅ already safe

**After**:
- `login.js` → `profile.circleWallet` + session `circleWalletId/Address` ✅
- `_circle.js:createUserWallet` → `deterministicUUID('elligentt:provision-wallet:'+userId)` ✅
- `provision.js` → per-user KV `provision_lock:{userId}` + 409 while in flight ✅
- `index.html` auth modal → Circle-first labels, no "Internal Smart Wallet" ✅

## 5. Internal-wallet creation paths eliminated from Autonoma

- New-user OTP: no internal wallet (already null; verified unchanged).
- Password login: now returns Circle identity, not a legacy address (the legacy `wallet.address`
  field remains only for historical record).
- Auth success modal: no "Internal Smart Wallet" label/fallback.
- Provisioning: no duplicate Circle wallets (deterministic idempotency + lock).

## 6. Circle provisioning behavior

- Stable identity: per-user `circleWalletId`/`circleWalletAddress` in KV, keyed by `user.id`.
- Deterministic idempotency key (Circle dedupe) derived from `userId`.
- KV `provision_lock` best-effort serialization (KV is not atomic — documented; the
  deterministic Circle idempotency key is the authoritative dedupe).
- Reconciliation: `functions/api/agent/[[path]].js:handleProvision` re-checks the Circle wallet
  on next provision and nulls invalid `circleWalletId` before re-provisioning.
- No fallback internal wallet when Circle fails — `provision` returns `502`/`409`, never a local key.

## 7. Legacy wallet compatibility & remaining risks

- Legacy `wallet.address`, vault data, and encrypted keys are **preserved** (not deleted).
- `createOrRestoreWallet` still only restores an existing vault (never creates).
- **REMAINING RISK (BLOCKED on scope):** `auth.js:_buildRemoteSigner` + `walletManager.activateFromAuth`
  still activate the legacy custodial signer for legacy users. This is consumed by the x402
  relayer (`_signRelayerAuth` → `signOnServer`), which Section 11 forbids changing. A full
  decoupling requires either (a) migrating the x402 relayer off the custodial signer, or
  (b) a narrowly-scoped compatibility layer that keeps `window.signer` for x402 while preventing
  Autonoma from surfacing it as the agent identity. **Not implemented pending authorization.**

## 8. Authentication compatibility

- OTP verification, password hashing, session cookie, OTP security: unchanged.
- `verify.js`/`login.js` now expose an identical profile shape (`wallet` + `circleWallet`).

## 9. Financial execution identity verification

- Autonoma execution already resolves the Circle signer via `SecureSignerProvider` (Circle mode)
  and `agentScheduleExecutor`/`aiSmartWallet` fail closed without a Circle signer (verified by
  existing `no-internal-wallet-regression.test.js`).
- No financial path was changed; authorization gates, spending limits, nonce handling and
  confirmation are untouched.
